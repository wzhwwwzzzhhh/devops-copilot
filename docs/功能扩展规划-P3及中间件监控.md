# 功能扩展规划 — P3 及中间件监控

> 当前项目已实现 MySQL 数据库的全方位监控（连接池、慢查询、死锁、执行计划、表健康）和基础 AI 排障流程。  
> 以下规划将覆盖更多中间件、基础设施和运维自动化场景，使 DevOps Copilot 成为真正的全栈运维助手。

---

## 一、当前能力边界

| 领域 | 已实现 | 未实现 |
|------|--------|--------|
| MySQL 监控 | 连接池、慢查询、死锁、EXPLAIN、表健康、运行中查询 | — |
| MySQL 运维 | KILL、加索引、ANALYZE、OPTIMIZE、缓存预热 | — |
| Redis | 配置项就绪（spring-data-redis + Lettuce），StateManager 用 Redis 存储会话 | 无独立监控面板，无 Key 分析、慢日志、内存分析 |
| Elasticsearch | RAG 知识库索引、经验记忆索引 | 无集群健康监控、索引性能分析、查询慢日志 |
| RabbitMQ | 配置项就绪 | 无队列监控、消费延迟、消息积压告警 |
| Docker | Dockerfile 就绪 | 无容器管理、日志查看、资源监控 |
| K8s | — | 完全未实现 |
| Linux 主机 | — | 无 CPU/内存/磁盘/网络监控 |
| Nginx | 访问日志分析、QPS 监控、状态码分布、延迟分析 | — |
| SSL 证书 | 到期监控、分级告警、多域名管理 | 无自动续期 |
| 部署流水线 | Mock 部署（scale/rollback/restart） | 无真实 CI/CD 对接 |
| 告警聚合 | 多源告警聚合、静音管理、严重级别过滤 | 无自动通知渠道 |

## 三、Phase 1 — 中间件监控补齐（2周）

### P3-1: Redis 深度监控

**目标**：Agent 能查看 Redis 运行状态、慢日志、Key 分布、内存分析、执行 Redis 命令。

```
监控维度：
1. INFO ALL → 解析 Server/Memory/Stats/Clients/CPU 段
2. SLOWLOG GET 10 → 慢查询 Top 10
3. INFO KEYSPACE → 各 DB 的 Key 数量
4. MEMORY STATS → 内存使用详情（需 Redis 4+）
5. CLIENT LIST → 当前客户端连接
6. SCAN / TYPE → 大 Key 扫描

操作维度：
1. FLUSHDB / FLUSHALL（需确认）
2. DEL key（删除指定 Key）
3. SET / EXPIRE（设置缓存）
4. CONFIG GET/SET（在线修改配置）
```

**涉及文件**：
- 新增 `RedisService.java` — 模仿 `DatabaseService`，通过 `LettuceConnectionFactory` 或 `Jedis` 执行命令
- 新增 `RedisMonitorController.java` — REST 端点
- 前端新增 `RedisDashboard.tsx`
- `ToolRegistry.java` — 注册 `check_redis_status`、`execute_redis_command` 工具
- `App.tsx` → nav 增加 Redis 监控入口

**依赖**：项目中已有 `spring-boot-starter-data-redis` + `lettuce-core`

---

### P3-2: RabbitMQ 监控

**目标**：Agent 能查看队列积压、消费者状态、连接数、消息速率。

```
监控维度（通过 RabbitMQ Management REST API /api/queues, /api/nodes, /api/connections）：
1. 队列列表 → 消息数、消费者数、Unacked 数
2. 节点状态 → 内存使用、磁盘可用、文件描述符
3. 连接概览 → 连接数、信道数
4. 消息速率 → Publish/Confirm/Deliver 速率
5. 未消费消息最多的 Top 5 队列

操作维度：
1. 清除队列消息（Purge）
2. 设置队列最大长度
3. 查看死信队列
```

**涉及文件**：
- 新增 `RabbitMQService.java`
- 新增 `RabbitMQController.java`
- 前端新增 `RabbitDashboard.tsx`
- `ToolRegistry.java` — 注册 `check_rabbitmq_status` 工具

**依赖**：RabbitMQ 需启用 `rabbitmq_management` 插件，提供 HTTP API

---

### P3-3: Linux 主机监控

**目标**：Agent 能查看主机的 CPU、内存、磁盘、网络、进程等系统级指标。

```
监控维度：
1. CPU → 整体使用率、Load Average、Top 5 进程
2. 内存 → 总计/已用/可用/Swap
3. 磁盘 → 各分区使用率、Inode 使用率、IO Wait
4. 网络 → 带宽使用、连接数(TCP/UDP)、丢包率
5. 进程 → Top 5 CPU/内存占用进程

采集方式：
- 方案 A（推荐）：主机部署 Agent（Shell/Python 脚本），定期上报到 Copilot API
- 方案 B（轻量）：通过 SSH 执行命令采集
```

**涉及文件**：
- 新增 `SystemMonitorService.java` — 解析 `/proc/stat`、`/proc/meminfo`、`df`、`netstat` 等
- 新增 `SystemMonitorController.java`
- 前端新增 `SystemDashboard.tsx`
- `ToolRegistry.java` — 注册 `check_system_status` 工具

## 四、Phase 2 — ES 深度 + Docker 容器管理（2周）

### P3-4: Elasticsearch 深度监控

**目标**：Agent 能查看 ES 集群健康、索引性能、查询慢日志、分片分布。

```
监控维度：
1. 集群健康 → status(green/yellow/red)、节点数、分片数
2. 节点状态 → heap 使用、CPU、磁盘、GC 情况
3. 索引性能 → 索引速率、搜索速率、拒绝数
4. 慢查询 → Search/Indexing 慢日志
5. 分片分布 → 未分配分片、大分片 Top 10

操作维度：
1. 强制合并段（Force Merge）
2. 重新路由分片
3. 更新索引 setting（副本数、刷新间隔）
4. 清理旧索引（基于保留天数）

注意：项目已有 RagService 做文档搜索，此模块是 ES 基础设施本身的监控
```

**涉及文件**：
- 新增 `ESMonitorService.java` — 调用 ES `/ _cluster/health`、`/_cat/indices`、`/_nodes/stats` 等 API
- 新增 `ESMonitorController.java`
- 前端新增 `ESDashboard.tsx`

---

### P3-5: Docker 容器管理

**目标**：Agent 能查看容器状态、日志、资源占用，执行启动/停止/重启操作。

```
监控维度（通过 Docker Engine API /containers/json, /containers/{id}/stats）：
1. 容器列表 → 状态、镜像、端口映射、启动时间
2. 资源占用 → CPU%、内存%、网络 IO、磁盘 IO
3. 容器日志 → 实时日志流（最近 100 行）
4. 镜像列表 → 大小、层数、创建时间

操作维度：
1. 重启容器
2. 停止/启动容器
3. 查看容器日志
4. 清理未使用的镜像和容器（docker system prune）

实现方式：
- 方案 A：通过 Docker Engine Unix Socket（localhost）或 TCP 连接
- 方案 B：通过 docker-java SDK
- 方案 C：通过 SSH 执行 docker 命令（最通用）
```

## 五、Phase 3 — K8s 集群监控 + 部署流水线（2周）

### P3-6: Kubernetes 集群监控

**目标**：Agent 能查看 K8s 集群状态、Pod/Service/Deployment 运行情况、事件日志。

```
监控维度：
1. 集群概览 → Node 状态、Pod 分布、资源容量
2. Pod 状态 → Running/Pending/CrashLoopBackOff 统计
3. Deployment → 期望/当前副本数、更新策略
4. Service/Ingress → 暴露方式、Endpoint
5. 事件 → Warning 事件、OOM、拉取失败
6. 资源使用 → Node CPU/Memory 请求和限制

操作维度：
1. kubectl describe pod → 排查 Pod 启动失败
2. kubectl logs → 查看 Pod 日志
3. kubectl exec → 进入容器执行命令
4. kubectl rollout restart → 滚动重启
5. kubectl scale → 扩缩容
6. kubectl delete pod → 重启异常 Pod

实现方式：
- 通过 K8s API Server + RBAC Token
- 使用 kubernetes-client/java（fabric8）或 REST API
- 通过 kubeconfig 认证
```

**涉及文件**：
- 新增 `K8sService.java` — 调用 K8s API
- 新增 `K8sController.java`
- 前端新增 `K8sDashboard.tsx`
- `ServiceConnection` 实体新增 `k8s` 类型
- `ToolRegistry.java` 注册 `check_k8s_status`、`k8s_scale`、`k8s_restart` 等工具

### P3-7: 真实部署流水线

**目标**：替代当前 Mock 的 `DeployService`，对接真实部署环境。

```
实现方式：
1. 对接 K8s API → 执行 Deployment 滚动更新/回滚
2. 对接 Docker Compose → 重启服务
3. 对接 SSH → 在远程服务器执行部署脚本

编排支持：
1. 蓝绿部署
2. 灰度发布（金丝雀）
3. 版本回滚
4. 健康检查自动判断

安全机制：
1. 审批流（已有 AWAITING_APPROVAL 节点）
2. 操作审计日志
3. 熔断保护（连续失败自动停止）
4. 变更时间窗口限制
```

## 六、Phase 4 — Nginx + SSL + 告警聚合（1周） ✅ 已完成

### P3-8: Nginx 日志分析 ✅ 已实现

**目标**：Agent 能解析 Nginx 访问日志，分析 QPS、错误率、耗时分布、Top URL。

```
分析维度：
1. QPS（每秒请求数）
2. 状态码分布（2xx/4xx/5xx）
3. P50/P95/P99 响应时间
4. 请求最多的 Top 10 URL
5. 错误率最高的 Top 5 路径
6. 客户端 IP 访问频率（防爬虫分析）
```

---

### P3-9: SSL 证书监控 ✅ 已实现

**目标**：Agent 能检测 SSL 证书到期时间，提前告警。

```
实现方式：
1. 通过 openssl 或 Java SSLContext 连接目标域名获取证书
2. 解析证书有效期、颁发机构、SAN 域名
3. 到期前 30 天/14 天/7 天分级告警
4. 支持通配符证书和多域名证书
```

---

### P3-10: 告警聚合与通知 ✅ 已实现

**目标**：将各监控维度的告警统一管理，支持多渠道通知。

```
告警源：
- MySQL 异常（连接池 > 80%、死锁、慢查询激增）
- Redis 异常（内存 > 80%、OOM、连接数过高）
- RabbitMQ 异常（队列积压 > 阈值）
- ES 异常（集群 yellow/red、分片未分配）
- 主机异常（磁盘 > 85%、内存 > 90%、Load 过高）
- K8s 异常（CrashLoopBackOff、OOM、Node NotReady）

通知渠道：
1. 钉钉/飞书/企业微信 Webhook
2. 邮件
3. 系统通知（前端红点）

聚合策略：
1. 相同告警 30 分钟内合并为一条
2. 告警升级（持续 15 分钟 → 提醒，30 分钟 → 电话）
3. 静默机制（已有，扩展至所有告警源）
```

## 八、评估标准

| 模块 | 验收标准 |
|------|---------|
| Redis 监控 | "检查 Redis 内存" → Agent 返回内存使用率、Top 大 Key |
| RabbitMQ | "看看订单队列有没有积压" → Agent 返回队列消息数和消费者状态 |
| 主机监控 | "检查服务器负载" → Agent 返回 CPU/内存/磁盘使用率 |
| ES 监控 | "ES 集群健康吗" → Agent 返回 cluster status 和分片状态 |
| Docker | "重启 nginx 容器" → Agent 确认后重启并返回结果 |
| K8s | "订单服务 CrashLoopBackOff 了" → Agent 排查并返回根因 |
| 部署流水线 | "发布 v2.0 并逐步放量" → 灰度 10% → 50% → 100% |
| SSL | "检查所有域名证书" → 返回到期时间表和即将到期的列表 |
