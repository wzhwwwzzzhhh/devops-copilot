## 二、P0 — 面试必问，必须尽快补齐

### P0-1：EXPLAIN 执行计划分析

**目标**：Agent 能对慢查询执行 `EXPLAIN FORMAT=JSON`，分析是否走索引、扫描行数、Extra 信息，给出索引优化建议。

**实现方案**：

```
1. DatabaseService 增加 explainQuery(sql) 方法
   → 执行 EXPLAIN FORMAT=JSON SELECT ...
   → 解析 JSON 返回 access_type、rows、Extra、possible_keys 等
2. 新增 ToolRegistry 工具 explain_query
3. DbDashboard 增加"执行计划"卡片
4. Prompt 引导 LLM 在发现慢查询时自动调用 explain_query
```

**涉及文件**：
- `DatabaseService.java` — 新增 `explainQuery()` 方法
- `ToolRegistry.java` — 注册第 10 个工具
- `ReActNode.java` — 补充工具名列表
- `DbDashboard.tsx` — 新增执行计划展示卡片
- `application.yaml` — 无需改动

**验收标准**：
- 用户说"分析一下这条慢查询的索引使用情况" → Agent 调用 `explain_query` → 返回索引建议
- 看板中慢查询行支持点击查看执行计划

### P0-2：死锁检测

**目标**：Agent 能查询 MySQL 死锁信息和锁等待情况，定位死锁根因。

**实现方案**：

```sql
-- 死锁检测 3 个查询维度
1. SHOW ENGINE INNODB STATUS   -- 最近死锁信息（解析 LATEST DETECTED DEADLOCK 段）
2. SELECT * FROM information_schema.INNODB_LOCK_WAITS  -- 当前锁等待
3. SELECT * FROM performance_schema.data_locks         -- 当前持有锁
```

**步骤**：
```
1. DatabaseService 新增 detectDeadlocks() 方法
   → 解析 SHOW ENGINE INNODB STATUS 的 TEXT 字段
   → 提取死锁时间、涉及事务、等待资源、回滚事务
2. 新增 detect_lock_wait 工具
3. 集成到 check_db_status 的第 7 类数据
```

**涉及文件**：
- `DatabaseService.java` — 新增 `detectDeadlocks()` + 两个辅助解析方法
- `ToolRegistry.java` — 注册 `detect_lock_wait`
- `DbDashboard.tsx` — 死锁告警卡片

**验收标准**：
- 模拟死锁（两个事务互相等待）→ 问"检查是否有死锁" → Agent 返回死锁详情
- 看板中显示当前锁等待 TOP 5

## 三、P1 — 体验提升，建议在 P0 之后做

### P1-1：30秒定时采集 + 趋势图

**目标**：看板自动刷新，连接池使用率趋势折线图。

**实现方案**：
```
1. DbDashboard 前端增加 useInterval 轮询（30s）
2. 后端 /api/database/status 增加 cache[5] 存储最近 5 次采样
3. 前端用 ECharts 折线图展示连接池趋势
```

**注意**：不要在后端开定时任务采集，用前端轮询 + 后端内存缓存就好，避免多用户并发重复采集。

---

### P1-2：缓存刷新

**目标**：Agent 能执行 `SELECT * FROM some_table` 预热缓存 / 刷新 Redis 缓存。

**实现方案**：
```
1. DatabaseService 新增 warmUpCache() 方法
   → 执行 SELECT COUNT(*) FROM key_tables（预热 InnoDB Buffer Pool）
2. 如果需要 Redis 缓存刷新，通过 ServiceConnection 的 redis 连接发 FLUSHDB 命令
```

---

### P1-3：告警静默

**目标**：用户可以对特定告警说"这个我知道了，先静默 1 小时"，Agent 不再重复提醒。

**实现方案**：
```
1. InvestigationContext 增加 silencedAlerts Map<alertType, expireTime>
2. 每次采集数据后检查是否存在未静默的告警
3. 前端看板中告警行支持"静默"按钮
```

### P2-2：Redis + ES 跨会话长期记忆

**目标**：Agent 解决过的问题存入 ES/Redis，下次相同问题直接复用经验。

**实现方案**：
```

3. 有则直接提示"上次遇到过这个问题，方案是：..."
```
