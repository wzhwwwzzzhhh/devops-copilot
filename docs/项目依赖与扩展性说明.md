# DevOps Copilot - 项目依赖与扩展性说明

> 说明：这个项目要给别人用，需要维护什么？用户需要配置什么？中间件怎么接入？

---

## 一、项目自身依赖（必须）

项目运行**本身**需要的基础设施：

| 组件            | 用途                   | 获取方式                             | 能否跳过 |
|:------------- |:-------------------- |:-------------------------------- |:---- |
| **MySQL 8.0** | 存储工具调用日志、对话历史、服务连接配置 | 本地安装 或 `docker-compose up mysql` | ❌ 必须 |
| **Redis 7**   | 会话状态缓存（2h TTL）       | `docker-compose up redis`        | ❌ 必须 |
| **JDK 17+**   | 运行 Java 应用           | 下载安装                             | ❌ 必须 |
| **Maven**     | 构建项目                 | IDEA 自带 或 单独安装                   | ❌ 必须 |

### 启动步骤

```bash
# 1. 创建数据库
mysql -uroot -p -e "CREATE DATABASE IF NOT EXISTS devops_copilot CHARACTER SET utf8mb4;"

# 2. 启动 Redis（Docker）
docker run -d --name redis -p 6379:6379 redis:7-alpine

# 3. 启动应用
mvn spring-boot:run "-Dspring-boot.run.arguments=--cli"
```

## 二、可选依赖（增强功能，非必须）

| 组件                  | 用途        | 不配的话                              |
|:------------------- |:--------- |:--------------------------------- |
| **Elasticsearch**   | RAG 知识库检索 | 降级：知识库检索返回"暂不可用"，其他功能正常           |
| **Ollama / 任意 LLM** | 智能分析决策    | 降级：FallbackAnalyzer 基于数据分析，无模型也能跑 |
| **Docker**          | 一键启动中间件   | 手动安装 MySQL/Redis                  |

**项目设计原则：所有可选依赖都有降级方案，不会因为某个组件不可用而崩溃。**

## 三、用户需要配置的外部中间件（核心扩展性）

这是你提到的核心问题——不同用户的 MySQL / Redis / 日志路径都不一样。

### 方案：Service Connections API

用户通过 API 注册自己的中间件信息，项目动态读取：

```json
POST /api/connections
{
  "name": "生产环境 MySQL",
  "type": "mysql",           // mysql / redis / es / prometheus / k8s / log
  "host": "192.168.1.10",
  "port": 3306,
  "username": "root",
  "password": "xxx",
  "properties": {            // 不同类型的额外参数
    "logPath": "/var/log/mysql/slow.log",
    "database": "order_db",
    "labels": ["order-service", "production"]
  }
}
```

### 支持的服务类型

| 类型           | 示例                | 用于哪个工具                            |
|:------------ |:----------------- |:--------------------------------- |
| `mysql`      | MySQL 连接信息        | check_db_status                   |
| `redis`      | Redis 连接信息        | check_db_status                   |
| `es`         | Elasticsearch 地址  | search_knowledge                  |
| `prometheus` | Prometheus API 地址 | query_metrics                     |
| `k8s`        | Kubernetes API 信息 | list_deployments / execute_action |
| `log`        | 日志文件路径            | query_logs                        |
| `service`    | 微服务信息             | 通用路由                              |

### 工具层如何对接

现在工具从 Mock 文件读数据，改造成**按用户配置连接真实系统**：

```
当前：
MetricsService.getMetrics("order-service")
  → 读取 mock/metrics/order-service.json

改造后：
MetricsService.getMetrics("order-service")
  → 从 ConnectionRepository 查找 type=prometheus 且 labels=order-service 的连接
  → 用连接信息调真实的 Prometheus API
  → 如果没找到用户配置，降级读取 Mock 数据
```

### 数据流向

```
用户注册中间件 → MySQL connections 表
    ↓
工具调用时 → 查用户配了什么 → 有配置则连真实系统，没配置则读 Mock
    ↓
Mock 数据作为默认降级，新用户开箱即用
```

## 四、模型配置（可切换 LLM）

用户可以通过 API 动态添加和切换模型：

```json
POST /api/models
{
  "name": "通义千问",
  "provider": "openai",        // ollama / openai / custom
  "baseUrl": "https://dashscope.aliyuncs.com/compatible-mode/v1",
  "apiKey": "sk-xxxxx",
  "modelName": "qwen-max",
  "modelType": "chat"          // chat / embedding / reasoning
}

POST /api/models/current
{
  "modelType": "chat",
  "modelId": 1
}
```

当前 ChatService 硬编码了 `ollama.base-url` 和 `ollama.chat.model`，改造后从 `ModelConfig` 动态读取。Mock 数据作为 LLM 不可用时的最终降级。

## 五、知识库管理

用户可以通过 API 管理知识库文档：

```json
POST /api/knowledge
{
  "title": "MySQL 主从延迟处理方案",
  "content": "遇到主从延迟时的排查步骤和解决措施...",
  "tags": ["mysql", "主从", "延迟"]
}

GET /api/knowledge?keyword=mysql
DELETE /api/knowledge/doc-001
```

数据写入 ES，与 Tools 中的 `search_knowledge` 工具联动。

## 八、面试时可以说的

> **"我们这个项目的核心设计思路是插件化数据源。用户通过 API 注册自己的 MySQL、Redis、Prometheus 地址，工具层根据配置动态选择连接真实系统还是走 Mock 降级。这样新用户开箱即用，有真实环境的用户可以一键对接。加上 RAG 知识库和可切换的 LLM 模型，整个系统是一个可插拔的 AI Agent 框架。"**
