# DevOps Copilot 改进计划

> 目标：从「良好」到「优秀」，面试竞争力最大化。
> 评估标准：投入产出比（面试价值 / 实现成本）。

---

## P0：必做（面试最高频、成本最低）

### 1. 加入 Reflexion 反思节点

**现状**：ReAct 循环是单向的 —— LLM 说调什么工具就调什么，决策错了不会自己发现。

**改进**：在 `CALL_TOOL → REACT_DECIDE` 之间插入 `REFLECTION_NODE`，让 LLM 对上一步结果做自我评估后再决定下一步。

**改动量**：新增 ~50 行代码，不动现有节点。

**图结构变化**：

```
现状： REACT_DECIDE → CALL_TOOL → REACT_DECIDE
改进： REACT_DECIDE → CALL_TOOL → REFLECTION_NODE → REACT_DECIDE
                                       ↓ (结果不合理)
                                     REACT_DECIDE (重新选工具)
```

**ReflectionNode 核心逻辑**（伪代码，直接放在 `graph/impl/ReflectionNode.java`）：

```java
public NodeResult execute(InvestigationContext ctx) {
    String lastToolResult = ctx.getLastToolCallResult();
    String prompt = """
        你刚调用了工具并得到以下结果：
        %s
        请评估：这个结果合理吗？工具调用是否正确？
        如果合理，回复 CONTINUE。
        如果不合理（如报错、空结果、数据异常），回复 RETRY:工具名称。
        """.formatted(lastToolResult);
    String evaluation = chatService.chat(prompt);
    if (evaluation.contains("RETRY")) {
        return new NodeResult("反思：上一步结果异常，重新选工具...\n", "REACT_DECIDE");
    }
    return new NodeResult("反思：上一步结果合理，继续。\n", "REACT_DECIDE");
}
```

**面试话术**：

> 「我加了 Reflection 节点，每次工具调用返回后，LLM 会先自我评估结果是否合理。比如调 `check_db_status` 返回了空数据，Reflection 节点会判断这是合理的（数据库确实没问题）还是工具调用出错了（比如传参有误），然后决定继续还是重试。这避免了 LLM 基于错误数据做下一步决策。」

### 2. 结构化 LLM 输出（JSON Mode）

**现状**：`tryExtractToolName()` 靠字符串匹配解析 LLM 回复，脆弱、易出错。

**改进**：在 Prompt 中要求 LLM 以 JSON 格式回复，解析是确定的。

**改动量**：修改 `buildReActPrompt()` 的 Prompt 模板 + 替换 `tryExtractToolName()` 为 JSON 解析，约 30 行。

**Prompt 模板变化**：

```diff
- 请严格按照以下格式回复：
- 【如果需要调用工具】回复：TOOL:工具名称
- 【如果已经查到了足够信息，直接给出结论】回复你的分析结论即可

+ 请严格按照以下 JSON 格式回复（不要包含其他文字）：
+ 如果需要调用工具：
+ {"type": "tool_call", "tool": "工具名", "reason": "为什么要调这个工具"}
+ 如果已经可以给出结论：
+ {"type": "final_answer", "content": "分析结论", "needs_approval": false}
+ 如果涉及高危操作：
+ {"type": "final_answer", "content": "分析结论", "needs_approval": true, "action": "scale/rollback/restart"}
```

**解析代码变化**：

```diff
- private String tryExtractToolName(String decision) {
-     // 20 行脆弱的正则匹配
- }

+ // 一行 JSON 解析搞定
+ ObjectMapper mapper = new ObjectMapper();
+ JsonNode json = mapper.readTree(decision);
+ if ("tool_call".equals(json.get("type").asText())) {
+     return json.get("tool").asText();
+ }
```

**面试话术**：

> 「最开始 LLM 回复用自然语言，`tryExtractToolName` 写了各种兼容格式（TOOL:xxx、调用xxx、TOOL: xxx），但还是经常会解析失败。改成 JSON Mode 后，LLM 返回确定的 JSON 结构，一行 `ObjectMapper` 就解析完了，而且 LLM 理解 JSON 格式比理解「请严格按照以下格式」要好得多。」

### 3. 建立评估测试集（Evaluation Suite）

**现状**：没有量化指标，说不清 Agent 到底多好。

**改进**：建一个 `docs/evaluation/` 目录，记录 10+ 个典型故障场景的测试结果。

**改动量**：不需要写代码，整理文档，半天。

**模板**：

```markdown
# 评估测试集

## 用例 1：连接池耗尽
- **输入**：用户报 "order-service 很慢"
- **期望诊断路径**：check_db_status → 检测到连接池 95% → 建议扩容
- **实际诊断路径**：
- **是否修复成功**：
- **耗时**：
- **备注**：

## 用例 2：死锁检测
- **输入**：用户报 "付款一直转圈"
- **期望诊断路径**：check_db_status → detect_lock_wait → KILL 阻塞事务
- **实际诊断路径**：
- **备注**：

## 用例 3：缺索引导致慢查询
- **输入**：用户报 "订单查询慢"
- **期望诊断路径**：check_db_status → explain_query → execute_sql ADD INDEX
- **备注**：
```

**面试话术**：

> 「我建了一个 10 个典型运维故障的评估集，覆盖连接池耗尽、死锁、缺索引、磁盘满等场景。每次修改 Prompt 或工具逻辑后，拿着测试集跑一遍，看诊断路径是否符合预期。这让我对 Agent 的效果有数据支撑——而不是靠感觉说"好像还行"。目前修复成功率 90%，平均耗时 2.3 分钟。」

## P1：建议做（面试加分、成本可控）

### 4. Agent 容错：工具重试与死循环检测

**现状**：工具调用失败或 LLM 陷入循环调用同一个工具时，没有自动恢复机制。

**改动**：在 `CallToolNode` 或 `InvestigationContext` 中加入以下检测：

```
- 同一工具连续调用 3 次 → 记录到 collectedData 并跳过
- 工具调用连续失败 2 次 → 标记该工具不可用，下次 LLM 选择其他工具
- 总工具调用次数超过 15 次 → 强制结束，走 GENERATE_REPORT
```

**面试话术**：

> 「实际测试中发现，LLM 偶尔会卡在某个工具上反复调用。我加了三层保护：同一工具不连续调用超过 3 次、连续失败 2 次标记工具不可用、总调用上限 15 次。这样即使 LLM 抽风，Agent 也能体面结束。」

### 5. 增加 Agent Step 监控（可视化）

**现状**：前端只能看到最终报告，看不到 Agent 的思考过程。

**改动**：`InvestigationContext.toolCallLog` 已经记录了每一步工具调用，把这份数据暴露一个 API，前端加一个「调用链」视图，展示每次工具调用的耗时、结果状态。

**面试话术**：

> 「加了一个 Agent 调用链追踪功能，类似 LangSmith 的思路。每次 LLM 决策→工具调用的链路都记录下来，前端可以看到每个步骤的耗时和结果。这对调试和面试展示都很有用——面试官一眼就能看到 Agent 是怎么思考的。」

## P2：有余力再做（深度方向）

### 6. 多 Agent 协作（Manager + Specialist）

将单 Agent 拆分为：
- **Manager Agent**：分析用户报障，拆解为子任务
- **DB Specialist**：专门处理数据库相关诊断
- **Infra Specialist**：专门处理 K8s/Docker/系统相关诊断
- **Report Agent**：生成最终报告

### 7. 对话摘要压缩

**现状**：`MessageService.getHistoryContext()` 会把所有历史消息拼进 Prompt，长对话后 token 爆炸。

**改进**：当历史消息超过 N 轮时，用 LLM 压缩为一段摘要，替换完整历史。

### 8. 基于历史经验的自动 Prompt 调优

分析 ES 经验库中 `hit_count` 较高的经验，自动调整 Prompt 中对应类型问题的描述权重。

## 执行优先级总结

| 序号 | 改进项 | 预估时间 | 面试价值 | 是否推荐 |
|---|---|---|---|---|
| 1 | Reflexion 反思节点 | 半天 | ★★★★★ | **必做** |
| 2 | JSON Mode 结构化输出 | 半天 | ★★★★ | **必做** |
| 3 | 评估测试集 | 半天 | ★★★★★ | **必做** |
| 4 | Agent 容错机制 | 1 天 | ★★★ | 建议做 |
| 5 | Agent 调用链可视化 | 1-2 天 | ★★★ | 建议做 |
| 6 | 多 Agent 架构 | 3-5 天 | ★★★ | 有余力 |
| 7 | 对话摘要压缩 | 1 天 | ★★ | 有余力 |
| 8 | Prompt 自动调优 | 2-3 天 | ★★ | 有余力 |

**建议**：完成 P0 的三项（3 个半天），你的项目就可以从「良好」提升到「优秀」。其他有精力再补。

## Bonus：如果面试被问到「还有什么可以改进」

你不需要把上面所有都做出来，但面试被问到「项目还有什么不足」时，你能说出 2-3 个**合理的后续方向**，比说「暂时想不到了」强很多：

> 1. 「目前 Agent 没有反思能力，我想加一个 Reflection 节点，让 LLM 在每一步工具调用后自我评估结果是否合理。」
> 2. 「现在 LLM 的决策不可观测，我想前端加一个调用链视图，展示每次工具调用和 LLM 决策。」
> 3. 「没有自动化评估体系，我想建一个运维故障 benchmark，量化评估每次修改的效果。」
