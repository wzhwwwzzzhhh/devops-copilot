# DevOps Copilot 面试问答 — 架构与设计篇

> 问题范围：项目整体架构、ReAct vs Plan-and-Execute、图编排引擎、技术选型

---

### Q1：这个项目是做什么的？用 2 分钟讲清楚。

**Target：项目介绍，几乎必问，是面试的「第一印象」。**

> DevOps Copilot 是一个基于 AI Agent 的智能运维助手。核心流程是：用户输入报障信息（比如 "order-service 报错了"），系统通过 LLM 自主决策，动态调用 20 个运维工具进行诊断——检查数据库连接池、慢查询、死锁、日志、系统指标等。发现问题后自动给出修复建议，高危操作走 Y/N 人工审批，批准后自动执行（加索引、KILL 连接、扩容等），最后验证恢复效果。LLM 不可用时自动降级为规则引擎数据驱动分析，零依赖 LLM 仍可输出排障报告。
>
> 整个系统用 Spring Boot 3 构建，前端 React + TypeScript + ECharts 展示监控看板和图文混排的报告，数据层用 MySQL + Redis + Elasticsearch 三级存储。

### Q2：为什么选 ReAct 而不是 Plan-and-Execute？这是你自己做的决策还是参考了什么？

**Target：考察架构决策能力。这是整个项目最核心的问题。**

> 这是我调研后做的决策。核心原因是：**运维场景的故障表现和根因之间是非线性关系**。
>
> 比如用户报 "order-service 502"，可能的根因包括：数据库连接池耗尽、死锁导致事务堆积、慢查询占满 CPU、磁盘满、甚至只是负载均衡配置问题。如果用 Plan-and-Execute，LLM 需要在第一步就制定完整计划——但它那时候根本不知道真正的问题在哪。Plan 越早做越错，而且发现计划不对时回退成本很高。
>
> ReAct 的 **推理→行动→观察→再推理** 循环天然适合这种场景：LLM 先调一个工具看看结果，根据结果决定下一步。如果查了连接池发现正常，那就不需要走扩容分支，转而查日志。这种动态调整在运维场景下是刚需。
>
> 另外从成本角度，Plan-and-Execute 需要 LLM 参与规划阶段，而 ReAct 在我们的场景下 13 步完整诊断平均只需要 4-5 次 LLM 调用——因为确定性逻辑（连接池采集、慢查询解析）都前置到工具函数内了，LLM 只做分支决策。
>
> 选型依据参考了 ReAct 论文（Yao et al., 2023），也对比了当时 LangGraph 的 Plan-and-Execute 示例。

### Q3：图编排为什么自己写不用 LangGraph 或者 Spring AI 的 @Tool 注解？

**Target：考察框架选型的 thinking，不是考察知不知道 LangGraph API。**

> 两个原因。
>
> 第一，我的图结构非常简单——就是 13 个节点，每个节点实现一个 `Node` 接口返回 `NodeResult(nextNodeId)`，`Graph` 本质上就是一个 `Map<String, Node>`。引入 LangGraph 或者 Spring AI 的状态机反而带来了不必要的复杂性。手写版本 35 行代码就解决了，没有黑盒，调试时每一步都可以打断点看状态。
>
> 第二，框架依赖问题。如果用了 LangGraph 的 Java 版本（当时还不太成熟），LLM 接口绑定框架的抽象层，后面要切换模型供应商或者调整调用方式会很麻烦。我的方案里只依赖 Spring 的 DI，没有任何第三方 Agent 框架，所有逻辑都在代码里可见可控。
>
> 关于 Spring AI 的 @Tool——我没有用，因为我不想让工具调用绑定到框架的 Function Calling 机制。我的 ToolRegistry 是自己注册的 Lambda，格式灵活，可以兼容 Ollama 和 OpenAI 两种不同的 API 风格。

### Q4：20 个工具都是 Mock 吗？真实数据接入怎么做的？

**Target：考察「真实环境适配」意识。**

> 每个工具都采用 **真实连接优先，Mock 降级** 的双模设计。以 DatabaseService 为例，代码逻辑是：
>
> 先从数据库查 `ServiceConnection` 表看有没有配 MySQL 连接，有的话通过 JDBC 直连目标库执行 `SHOW STATUS`、`PROCESSLIST`、`performance_schema` 查询等 6 类 SQL 采集真实指标。没有配置时自动降级读 `resources/mock/` 下的 JSON 文件返回模拟数据。
>
> MetricsService 同理：先试 Prometheus 的 `/api/v1/query`，失败或未配置则读 Mock JSON。
>
> DeployService 同理：先试 K8s API 的 `/apis/apps/v1/namespaces/xxx/deployments/xxx/scale`，失败或未配置则走 Mock 模拟。
>
> 切换不需要改代码、不需要重启——在前端系统设置界面加一个服务连接记录就行。这也是为什么我没有把工具写死成纯 Mock 的原因，面试官如果问"这个项目是不是就是个 Demo"——我的回答是：有真实数据源接口，你的环境接上就能用。

### Q5：13 个节点为什么这么划分？不是越多越好也不是越少越好吗？

**Target：考察对系统复杂度的控制力。**

> 13 个节点对应了三种执行路径：
>
> **ReAct 主路径（5 个节点）**：START → REACT_DECIDE → CALL_TOOL → AWAITING_APPROVAL / EXECUTE_ACTION → GENERATE_REPORT → END。这是 LLM 驱动的诊断闭环。
>
> **健康巡检子图（6 个节点）**：HEALTH_CHECK_START → HEALTH_CHECK_METRICS → HEALTH_CHECK_LOGS → HEALTH_CHECK_DATABASE → HEALTH_CHECK_DEPLOYMENTS → HEALTH_CHECK_ANALYZE → GENERATE_REPORT。这是一条**确定性流水线**，不需要 LLM 参与路径决策。
>
> **快速查询（2 个节点）**：START → DIRECT_QUERY → GENERATE_REPORT。简单查个版本号、状态信息不经过 LLM。
>
> 这个划分是基于「职责单一」原则：每个节点只做一件事（决策、调工具、审批、生成报告），方便单独测试和替换。如果再细化（比如每个工具一个节点），13 个节点会膨胀到 30+，维护成本上升。如果再合并（比如 REACT_DECIDE 和 GENERATE_REPORT 合并），LLM 的职责不清晰。

### Q6：为什么健康巡检不走 ReAct 路径？

**Target：考察对 ReAct 适用边界的理解。**

> 健康巡检是一套完全确定的流程：采集 CPU/内存→查日志→查数据库→查部署状态→汇总分析。中间没有任何"根据上一步结果决定下一步做什么"的分支——你永远需要采集所有指标才能给出完整的巡检报告。所以用确定性图节点走一遍就够了。
>
> 如果用 ReAct，LLM 决定先去查日志，发现日志正常再查数据库——效率反而低，因为巡检就是要全量采集的。
>
> 不过报告生成环节仍然尝试用 LLM 生成结构化报告（HEALTH_CHECK_ANALYZE 节点调了 chatService），只是如果 LLM 挂了，`FallbackAnalyzer.analyzeHealthCheckData()` 纯 JSON 解析也能输出。

### Q7：为什么不用微服务架构，而是单体？

**Target：考察架构选型的合理性，不是考察会不会微服务。**

> 这个项目的定位是一个**运维辅助工具**，不是核心业务系统。用户的典型使用方式是：一个人或者一个小团队打开浏览器用。单体能做到：
> - 部署简单：一个 `mvn spring-boot:run` 就起来了
> - 不需要服务发现、配置中心、API Gateway 等基础设施
> - 工具调用和 LLM 调用都在进程内，没有网络开销
>
> 如果未来要接入多个机房、多团队使用，可以把 LLM 服务拆出去独立部署（因为它已经是通过 HTTP 调用的），其他工具调用也可以拆成独立服务。但现阶段单体是合适的。

### Q8：你提到了性能优化让 LLM 只调用 4-5 次。怎么做到的？

**Target：考察对 ReAct 实际应用的深度理解。简历上的数据，面试官一定会追问。**

> 核心思路是 **把确定性逻辑前置到工具函数内，LLM 只做分支决策**。
>
> 举个例子：`check_db_status` 这个工具内部一次 JDBC 调用就采集了 6 类指标（连接池、运行中查询、数据库大小、SQL 性能、表健康、慢查询日志）。LLM 只需要决定"我要不要调 check_db_status"，不需要决定"我要先查连接池、再查慢查询、再查表健康"——那些都在工具函数里串行做完了。
>
> 再比如 `detect_lock_wait`，工具内部一次调用 `SHOW ENGINE INNODB STATUS` + `information_schema.INNODB_LOCK_WAITS` 就返回了完整的死锁和锁等待分析。
>
> 这样 13 步诊断流程中，LLM 只需要做 4-5 次分支决策：先调什么→看到结果→再调什么→给出结论。其他步骤都是工具函数内部的确定性逻辑。
>
> 如果反过来，LLM 每一步只调一个原子工具（比如一个工具只查连接池，另一个只查慢查询），那 13 步可能要调 13 次 LLM，耗时和成本都翻倍。

### Q9：如果让你重新设计这个系统，你会改变什么？

**Target：考察复盘能力和技术视野。这题回答好了很加分。**

> 三点：
>
> 第一，**我会引入 Reflection 机制**。现在 ReAct 是单向的——LLM 说调什么工具就调什么，如果决策错了（比如应该在数据库层面排查，结果跑去查日志了），没有自我纠正机制。可以在 CALL_TOOL 和 REACT_DECIDE 之间插一个反思节点，让 LLM 评估上一步结果是否合理。
>
> 第二，**我会用 JSON Mode 替代字符串解析**。现在 LLM 回复靠 `tryExtractToolName()` 做正则和关键词匹配，虽然兼容了多种格式但很脆弱。改成 JSON 结构化输出后一行 `ObjectMapper` 就解析完了。
>
> 第三，**我会早期就建评估测试集**。现在 30 个故障的测试数据是后来才整理的。如果一开始就建好评估集，每次改 Prompt 或工具逻辑时能立刻知道有没有 regression——现在靠感觉，不够严谨。

### Q10：你提到模拟了 30 个故障，是怎么模拟的？覆盖率够吗？

**Target：考察评估方法的严谨性。**

> 30 个故障分为 5 类：缺索引（8 个）、长事务/锁等待（8 个）、死锁（4 个）、连接池耗尽（5 个）、磁盘/内存/系统异常（5 个）。模拟方式是构造数据——有真实 MySQL 时通过造数据模拟（比如制造慢查询、造死锁），无真实 MySQL 时修改 Mock JSON 文件让返回的数据呈现故障特征。
>
> 覆盖率是否够？对运维常见的数据库故障覆盖了 90% 左右。没有覆盖的包括：主从延迟、binlog 爆满、连接数打满等——这些在现有工具框架下只需要加一个 SQL 查询就能支持，架构层面不需要调整。
>
> 不过这个评估集是自己建的，不是行业标准。如果想做得更严谨，可以参照 Chaos Engineering 的思路引入随机故障注入。

### Q11：Spring AI 在这个项目里扮演了什么角色？如果去掉会怎样？

**Target：考察你对所用技术的真实掌握程度，有没有用对地方。**

> Spring AI 在这个项目里的作用非常有限——实际上只依赖了它的 dependency 管理，没有用它的 `@Tool`、`ChatClient` 或 Advisor 机制。我自己的 `ChatService` 是直接通过 `RestTemplate` 调用 LLM API 的，连 Spring AI 的抽象层都没走。
>
> 如果去掉 Spring AI，项目完全不受影响。当初引入主要是想后面可能需要 embedding 等功能，但实际上 embedding 一直没启用，项目就搁置了这个依赖。
>
> 这是一个可以优化的点——应该去掉不必要的依赖，减少项目复杂度。

### Q12：为什么不做成 IntelliJ IDEA 插件，而是 Web 应用？

**Target：考察产品形态选择是否合理。**

> Web 应用的选择有几个考虑：
>
> 第一，**生态位不同**。IDEA 插件的用户是开发者在写代码时用，而运维 Agent 的使用者是运维或 SRE 在值班时用——他们通常开着浏览器或者手机。Web 应用比 IDE 插件更适合这个场景。
>
> 第二，**可视化**。这个项目有大量的 ECharts 仪表盘——连接池趋势、慢查询分布、数据库大小对比——这些在 IDE 插件里很难做好，Web 应用天然适合做 dashboard。
>
> 第三，**部署方式更灵活**。一个 jar 包部署在跳板机上，团队所有人都能访问，不用每个人装插件。
>
> 不过对开发者来说，IDE 插件确实更方便"写代码时顺手看数据库状态"。这个可以作为后续扩展方向。

### Q13：你提到了 13 步诊断，能具体说出哪 13 步吗？

**Target：考察对项目的熟练程度，如果吞吞吐吐就减分。**

> 可以。13 步指的是 13 个图节点：
>
> ReAct 主路径（7 个）：START → REACT_DECIDE → CALL_TOOL → AWAITING_APPROVAL → EXECUTE_ACTION → GENERATE_REPORT → END
>
> 健康巡检路径（6 个）：HEALTH_CHECK_START → HEALTH_CHECK_METRICS → HEALTH_CHECK_LOGS → HEALTH_CHECK_DATABASE → HEALTH_CHECK_DEPLOYMENTS → HEALTH_CHECK_ANALYZE
>
> 加上 DIRECT_QUERY 总共 13 个。其中 HEALTH_CHECK_ANALYZE 和 GENERATE_REPORT 是复用的。

### Q14：如果用户连续说"Y"确认执行，会不会有安全问题？

**Target：考察对安全设计的思考深度。**

> 不会，因为有三层保护：
>
> 第一，审批是按**单次会话、单次操作**生效的——`InvestigationContext.isAwaitingApproval` 在确认或取消后会立即设为 false，不会跨操作保持。
>
> 第二，每个高危操作的触发必须在 ReActNode 中由 LLM 生成特定的分析文本才会进入审批流程。连续说"Y"最多执行当前这一项操作，不会执行其他未授权的操作。
>
> 第三，SQL 执行有白名单，`executeSafeSQL()` 的正则只允许 7 种操作。就算用户确认了 KILL 某个连接，这个 KILL 也必须走白名单校验。
>
> 实际上最危险的操作不是 KILL 或者加索引——那些都是**可逆的**。最危险的操作是 DROP TABLE，而白名单里虽然允许 DROP TABLE IF EXISTS，但它只对指定表生效。如果担心这个问题，可以在白名单中移除 DROP TABLE 和 CREATE TABLE，保留运维常用的 ADD INDEX / ANALYZE / KILL 就够了。

### Q15：如果用户报了一个这个系统没见过的故障类型，LLM 能处理吗？

**Target：考察对 LLM 泛化能力的理解。**

> 分两种情况。
>
> 如果这个故障类型可以被**现有的 20 个工具的组合**诊断出来——比如某个服务 CPU 飙高、但数据库正常——LLM 可以通过调 system_monitor 看到 CPU 高，调 query_logs 看到日志异常，综合分析得出结论。ReAct 的优势就在这里：它不依赖预设的故障模板，而是通过工具组合来覆盖未知场景。
>
> 但如果这个故障需要的工具不在 20 个工具里——比如需要查特定的第三方 API——那 LLM 没办法，因为它不能动态创建新工具。这是当前架构的边界。
>
> 解决方案有两个：一是把工具注册做成可扩展的（通过 `@Tool` 注解自动扫描或 SPI 机制），二是引入代码生成让 LLM 自己写工具代码执行——但这引入了安全风险，需要沙箱。
